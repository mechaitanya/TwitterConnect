# API coverage matrix

Source of truth: the official X API OpenAPI document (`https://docs.x.com/openapi.json`, version **2.175**). This file is generated by `tools/generate_coverage.py` from that document, from the routes found in `src/XConnect`, and from the tests; do not edit it by hand. `docs/spec-snapshot.json` holds the compact snapshot that `SpecConformanceTests` checks the code against on every test run.

**Total: 268 operations. Access-restricted: 6, Not applicable: 1, Not implemented: 82, Not supported: 47, Supported: 132.**

> This is **not** full coverage of the specification. Every *Supported* row is implemented and tested; every other row is listed with its reason.

## How to read this

- **Auth** and **Scopes** are what the OpenAPI document lists for the endpoint. The SDK only sends an endpoint the authentication methods that are a subset of these (checked by `SpecConformanceTests`), and throws `InvalidOperationException` before sending when none of your configured methods qualifies. Scopes are requested when you authorise (see `XScopes`); the SDK cannot check that a token holds them, so a missing scope surfaces as an API error (`403`).
- **Rate limit.** X documents per-user limits for OAuth 1.0a / OAuth 2.0 user tokens and per-app limits for Bearer tokens, separately for each endpoint, reported in `x-rate-limit-limit/-remaining/-reset`. The SDK tracks the latest values per `METHOD route` in `client.RateLimits` and on every `XResponse.RateLimit`. Concrete numbers are plan-specific and are not in the OpenAPI document, so they are not repeated here.
- **Access** records only what X documents or the OpenAPI document states; otherwise availability depends on your X plan and permissions. X answers `403` when your plan lacks access.
- **Tests** counts calls to the SDK member in `tests/XConnect.Tests` (all stubbed; nothing here has been exercised against the live API in this repository's automated tests, see `docs/integration-testing.md`).

## Partially supported operations

- `POST /2/tweets`: every request field is modelled except `reply.auto_populate_reply_metadata`, which the documentation says is accepted but dropped before the request is processed. `media.call_to_actions` supports the `app_install`, `visit_site` and `watch_now` variants.
- `POST /2/media/metadata`: alt text, download status, content expiration, domain restrictions, found-media origin, management info, shared info and upload source. `audience_policy`, `geo_restrictions`, `sensitive_media_warning`, `sticker_info` and `preview_image` are untyped objects in the specification and are not exposed.
- `GET /2/tweets/analytics`, `GET /2/media/analytics`: all documented metrics are modelled; media counters are `JsonElement` because the API returns an integer or the original string.
- Compliance: create, list, get and cancel jobs, plus upload and download through the pre-signed URLs. Result files are returned as a raw stream (their format is not specified).
- Response models: for 123 operations every documented response field is modelled except `associated_metadata` on the media metadata result. Fields the specification leaves as untyped objects (`article`, `article_title`, and a Post's `organic_metrics`, `non_public_metrics`, `promoted_metrics`) are exposed as `JsonElement`.
- Webhooks and Account Activity: management calls only; receiving events is outside the SDK (`XWebhookSecurity` handles the CRC and signature checks). Not exercised live.
- News and usage: untyped parts of the schema (`contexts`, `keywords`, daily usage lists, free grants) are exposed as `JsonElement`.

Every supported operation is called by at least one test.
